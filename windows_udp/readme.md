# 项目介绍
BroadcastReceiver 广播接收方
BroadcastSender 广播发送方
BroadcastReceiver2 广播的回包，广播接收方
BroadcastSender2 广播的回包，广播发送方
BroadcastReceiver3 发现之后的可靠单播，接收方（按序号应答，重复包只补 ACK）
BroadcastSender3 发现之后的可靠单播，发送方（等 ACK，超时重发）

# 什么是“广播的回包”
“广播的回包”是指：一方先发 UDP 广播去找人，收到广播的一方再给发送方回一个应答包。现在这两个程序BroadcastSender和BroadcastReceiver只做了前半段，发送方发出去就关套接字，接收方只打印、不回答。

## 现在缺的是什么

`BroadcastSender` 把报文发到 `255.255.255.255:9000`，然后立刻 `closesocket`。`BroadcastReceiver` 在 9000 上 `recvfrom`，已经拿到了发送方的地址和端口，但没有用这个地址回包。

UDP 广播本身没有“连接”。回包靠的是 `recvfrom` 填出来的对方地址：接收方用同一个套接字 `sendto` 回去，发送方在原来的套接字上继续 `recvfrom`。

```
发送方                          局域网里每个接收方
  |  广播: "谁在？"  ----------------->  收到
  |  <-----------------  单播回包: "我是设备 A，IP=..."
  |  <-----------------  单播回包: "我是设备 B，IP=..."
```

回包一般是单播，发给广播发送方的 IP 和源端口，不是再广播一次。多台机器都会回，所以发送方要循环收，直到超时。

## 接收方怎么回

`recvfrom` 已经把对方地址放进 `senderAddr`（IP 和源端口都在里面）。收到请求后直接回这个地址：

```cpp
const std::string reply = "I am here";
int sent = sendto(
    sock,
    reply.c_str(),
    static_cast<int>(reply.size()),
    0,
    reinterpret_cast<const sockaddr*>(&senderAddr),
    senderLen);
```

回包不需要 `SO_BROADCAST`。源端口会是接收方绑定的 9000，目的地址就是刚才那个广播发送方。

## 发送方怎么收

套接字在第一次 `sendto` 之后，系统会分配一个临时本地端口。接收方看到的就是这个端口，回包也会回到这个端口。所以必须用发广播的那个套接字来收，不能发完就关。

```cpp
DWORD timeoutMs = 2000;
setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO,
    reinterpret_cast<const char*>(&timeoutMs), sizeof(timeoutMs));

sendto(...);  // 现有广播

while (true) {
    sockaddr_in from{};
    int fromLen = sizeof(from);
    int len = recvfrom(sock, buffer, sizeof(buffer) - 1, 0,
        reinterpret_cast<sockaddr*>(&from), &fromLen);
    if (len == SOCKET_ERROR) {
        int err = WSAGetLastError();
        if (err == WSAETIMEDOUT)
            break;   // 2 秒内没有新回包，收集结束
        // 其它错误再处理
        break;
    }
    // 打印来自谁、回了什么
}
```

`WSAETIMEDOUT` 在这里是正常结束，不是失败。一台机器回一次，多台就多收几次。

## 实际做的时候注意这几件事

1. **请求和应答要能区分。** 例如请求以 `DISCOVER` 开头，应答以 `HERE` 开头。否则有人把应答也广播出去时，接收方会把应答再当成请求，来回对打。
2. **同一台电脑上互测会收到自己的广播。** 发送方如果也绑了 9000，就会收到自己发出的包。可以比对源 IP，或者只对 `DISCOVER` 回包。
3. **防火墙要放行 UDP 9000 入站。** 广播发出去成功，不代表回包能进来。
4. **广播过不了路由器。** `255.255.255.255` 只在当前子网有效。公司若指定了定向广播（例如 `192.168.1.255`）或固定回包端口，以协议文档为准；没写的话，就回 `recvfrom` 给出的那个地址和端口。

# 可靠单播：应答、超时、重试（项目 3）

`sendto()` 返回成功，只说明本机 UDP 协议栈收下了这份数据报，并且替你交了出去。网线、交换机、对方进程、对方防火墙都还可能把它弄丢。UDP 头里没有“对方已收到”这一栏，所以可靠要自己做。项目 3 做的是最常见的一种：**停等**。发出一条，等到和它对得上的应答，超时就重发同一条；没有应答之前不发下一条。

广播仍然只用来找人。找到之后，可靠传输是发给这一台的单播。局域网里有多台接收方时，发送方采用第一份 `HERE`，其余机器不会收到后面的 `DATA`。

## 两个阶段

```
发送方                                      接收方（绑定 9001）
  |  DISCOVER <会话号>  广播 -------------->  记下会话号，序号期待改为 1
  |  <----------------  HERE <会话号> 计算机名
  |
  |  DATA <会话号> 1 reading-1  ----------->  第一次见到序号 1：交付，回 ACK
  |  <----------------  ACK <会话号> 1
  |
  |  DATA <会话号> 2 reading-2  ----X 丢了
  |  等 500 ms，没有序号 2 的 ACK
  |  DATA <会话号> 2 reading-2  重传 ------>  若序号 2 已经交付过：只补 ACK
  |  <----------------  ACK <会话号> 2
```

发现和数据用同一个套接字。第一次 `sendto` 之后，系统给发送方分配临时本地端口，`HERE` 和 `ACK` 都回到这个端口。所以发现成功之后不能 `closesocket`。

端口是 **9001**，和项目 2 的 9000 分开，两个接收方可以同时开着。本机有多块网卡时，`HERE` 的源地址是接收方实际回包的那块网卡，后面的 `DATA` 就发往这个地址。

## 报文

全部是一行文本，空格分隔。载荷本身可以再含空格。

| 方向 | 格式 | 作用 |
| --- | --- | --- |
| 发送方 → 广播 | `DISCOVER <会话号>` | 找一台接收方 |
| 接收方 → 单播 | `HERE <会话号> <计算机名>` | 发现应答，会话号必须和请求一致 |
| 发送方 → 单播 | `DATA <会话号> <序号> <载荷>` | 一条业务数据 |
| 接收方 → 单播 | `ACK <会话号> <序号>` | 确认已经可以负责这个序号 |

会话号是发送方启动时取的 `GetTickCount()`。接收方看到**新的**会话号，就把“下一个要交付的序号”重置为 1。因此接收方可以一直运行，发送方多开几次也是新的一轮。同一会话里如果 `DISCOVER` 因没收到 `HERE` 而重发，接收方不会把进度清掉。

序号从 1 开始，示例里依次发送 `reading-1`、`reading-2`、`reading-3`。

## 发送方怎么等、怎么重发

发现：最多广播 3 次，每次发出去之后等 1000 ms。这 1000 ms 是截止时间，不是“每收到一个杂包就重新计时”。等到第一份会话号相同的 `HERE` 就停，记下 `recvfrom` 给出的地址，后面的 `DATA` 发往这个地址。3 次都没有 `HERE`，整个程序失败，一条 `DATA` 都不会发。

数据：每一条单独停等。

1. 组 `DATA <会话号> <序号> <载荷>` 并 `sendto` 给发现到的那台。
2. 在 500 ms 截止时间之前收包。只有来自那台、会话号和序号都相同的 `ACK` 才算这条成功。旧序号的 ACK、别人的包、`HERE`，都丢掉继续等，直到截止时间。
3. 截止时间到了还没有匹配 ACK，就重发**同一条** `DATA`。
4. 最多发送 4 次（首次 + 3 次重试）。4 次都没有 ACK，放弃这一条，后面的序号也不再发。

500 ms 对局域网很宽。正常来回往往几毫秒；留这么多，是为了让一次调度延迟或一次故意丢包不会立刻被当成失败。4 次都失败时，这一条约占用 2 秒。

`SO_RCVTIMEO` 不能写成 0。在 Windows 上 0 表示一直阻塞，超时逻辑会失效。剩余等待时间已经是 0 时，直接当超时。

## 接收方怎么应答、怎么去重

`ACK` 的意思是“这个序号我已经收下了，你可以发下一个”。它不是“我刚打印了一行”。所以下面三种情况要分开：

1. **序号等于期待值**（新数据）：交付一次，期待值加 1，回 `ACK <会话号> <这个序号>`。示例里的“交付”就是打印 `Deliver seq=...`。
2. **序号小于期待值**（重复包）：数据已经交付过。常见原因是接收方的 ACK 在路上丢了，发送方超时后重传了同一条。这时必须再回一次同样的 ACK，否则发送方会一直重传到放弃。不能再次交付。
3. **序号大于期待值**：中间有空洞。停等的发送方本来不会跳号。这种包不回 ACK，避免发送方误以为空洞里的数据已经到达。

只对当前会话的 `DATA` 做上述处理。还没收到过 `DISCOVER`，或者 `DATA` 的会话号对不上，就忽略，也不要回 ACK。

## 这套做法保证什么、不保证什么

能保证的是：在接收方进程还活着、网络最终能通的前提下，选中的那一台会按 1、2、3 的顺序各交付一次，发送方也会等到对应 ACK 才发下一条。UDP 校验和负责丢掉损坏的数据报；序号负责丢掉重复包，并发现“这一条还没被确认”。

不能靠它得到的有：

- 广播本身发给子网里的每一台都可靠。这里只对第一份 `HERE` 的那台做停等。
- 对方进程崩溃之后的恢复。4 次超时后发送方放弃，不会无限重试。
- 更高吞吐。停等在往返时间很长时会空等。窗口协议（回退 N、选择重传）才允许多条同时在路上，这个示例故意没做。
- 加密和身份。任何能把 `ACK` 发到发送方临时端口的人，都可以让发送方以为数据已经送达。

## 故意丢一次，用来看见重试

同一台电脑上跑，ACK 通常第一次就回来，日志里会全是 `attempt 1/4`。接收方可以加一个参数，让每个序号只失败一次，第二次仍按正常规则处理。两种参数都只影响第一份；如果每一份都丢，重传也会失败，发送方会放弃。

| 参数 | 第一份 DATA 怎么处理 | 重传时接收方日志 |
| --- | --- | --- |
| `--drop-first` | 整包丢掉，不交付、不回 ACK | `Deliver`，这是第一次真正收下 |
| `--drop-ack` | 交付，但是不回 ACK | `Duplicate ... resend ACK`，不再交付第二次 |

## 测试方法：可靠单播（项目 3）

先启动 `x64\Debug\BroadcastReceiver3.exe`，再启动 `x64\Debug\BroadcastSender3.exe`。不要同时再开一个接收方占用 9001。防火墙需要放行这两个程序的 UDP 9001。

发送方正常结束时会打印 `Delivered 3/3`。接收方对应三次 `Deliver seq=1`、`2`、`3`。

要看数据报丢失：接收方用 `x64\Debug\BroadcastReceiver3.exe --drop-first` 启动。发送方每一条在第 2 次发送时收到 ACK，接收方先打印 `[drop]`，再对重传打印 `Deliver`。

要看应答丢失：接收方用 `x64\Debug\BroadcastReceiver3.exe --drop-ack` 启动。接收方对第一份打印 `Deliver` 和 `[drop-ack]`，对重传打印 `Duplicate`，每个序号仍然只交付一次。发送方同样在第 2 次发送时收到 ACK。

接收方不用关，再次启动发送方即可。新的会话号会让接收方把期待序号重置为 1，三份数据会再交付一次。
